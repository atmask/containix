Nix flakes,
running as Kubernetes containers.

containix is a containerd shim that resolves Nix flakes into pod rootfs at runtime. No image builds. No registries. No layers. Just a flake reference and the closure your binary cache already has.

The shape of it

Reference a flake. Skip the registry.

Drop a RuntimeClass on a pod and point at a flake. The shim does the rest.

The old way

Write a Dockerfile. Build. Push to a registry. Wait for the pull. Cache miss? Wait again.

# Dockerfile
FROM alpine:3.19
RUN apk add --no-cache myapp
CMD ["/usr/bin/myapp"]

# later, in CI…
$ docker build -t registry.acme.co/myapp:v1 .
$ docker push registry.acme.co/myapp:v1
$ kubectl apply -f pod.yaml
$ # wait for ImagePull…

With containix

Reference your flake. The shim resolves the closure from your binary cache and assembles a rootfs in place.

apiVersion: v1
kind: Pod
metadata:
  name: my-app
  annotations:
    containix.dev/flake: "github:myorg/myapp#default"
    containix.dev/entrypoint: "/bin/myapp"
spec:
  runtimeClassName: containix
  containers:
  - name: app
    image: "containix/empty:1.0.0"  # 49-byte stub
How it works

Five steps from pod spec to running container.

containix slots in as a containerd shim v2 runtime — the same interface runc uses. A RuntimeClass routes opted-in pods to the shim.

1

Read annotation

Shim reads containix.dev/flake from the pod spec.

→
2

Resolve closure

Runs nix build to fetch store paths from the binary cache.

→
3

Assemble rootfs

Bind-mounts the Nix closure as the container filesystem.

→
4

Generate spec

Writes an OCI runtime spec with the entrypoint and env.

→
5

Hand off to runc

Standard container lifecycle from here. No magic at runtime.

Why bother

The pieces you don't have to build.

No image builds

Skip the Dockerfile, the layer dance, and the registry round-trip. Your flake is the artifact.

Reproducible by default

Same flake lock → same closure → same rootfs. No "works on my machine" between build and prod.

Share store paths across pods

Two pods running the same library? They mount the same store path. One copy on disk.

Minimal attack surface

Pods get exactly the closure they declared — no shells, package managers, or surprise tools baked in.

Fast cold starts

Closures come from your binary cache, not a registry pull. Warm node, warm start.

Standard k8s on the outside

Just a RuntimeClass and an annotation. Same scheduler, same networking, same kubectl.

Status

Early development. containix is consumable today as packages.default and a nixosModule, with ~91% test coverage across the core packages. The API will change before v1. Pin commits, not branches.
